# TeamsMessageHistory - Teams メッセージ本文の残存履歴を端末の保存データから出す

Teams のメッセージへのリンク（メッセージの「…」→「リンクをコピー」）を一度貼ると、この PC に残っている
Teams の保存データを読み取り専用で読み、同じメッセージ ID の本文がどの版として残っているか（編集前・編集後など）を
全文と根拠付きで `result.txt` に出します。読むのは次の 2 種類で、結果は 1 つのフォルダーにまとまります。
そのうえで、同じデータから「スレッド全体の探索」を行い、対象そのものとは確認できない関連の文面も別枠で出します（0.1.7 から）。

- 本文の保存先である WebView2 プロファイルの IndexedDB / LevelDB（保全コピーを取ってから解析）。ここで見つかったものが「本文候補」です。
- それ以外に端末に残りうる痕跡: Windows の通知データベースと、同じプロファイルのキャッシュ（HTTP キャッシュ・Service Worker の CacheStorage）。圧縮された応答も展開して探します。ここで見つかったものは「痕跡の本文（未確認）」として、本文候補とは分けて出します。
- スレッド全体の探索（上の 2 種類のデータを読み直す）: 対象のメッセージ ID を別の項目に持つ記録（通知の一覧の抜粋、引用、リンクなど）、同じスレッド（親投稿 ID）や同じ会話の記録、入力した言葉を含む文面を、項目名に関係なく集めます。ここで見つかったものは「スレッド全体の探索（未確認）」として、本文候補とも痕跡の本文とも分けて出します。

- 通信はしません。リンクはローカルで分解するだけで、どこにも送りません。
- Teams の原本は読むだけです（変更・削除・起動・終了をしません）。IndexedDB は複製に対して解析し、通知データベースとキャッシュはその場で読み取り専用に走査します。
- 管理者権限、インストール、追加のランタイムは不要です。Windows 10/11 の Windows PowerShell 5.1 と .NET Framework で動きます。
- 残っているものしか出せません。旧本文が消えていれば出せず、回収を約束するものではありません。

## 使い方

1. フォルダーごと任意の場所に置き、`TeamsMessageHistory.bat` をダブルクリックします。
2. Teams でメッセージの「…」→「リンクをコピー」で取ったリンクを貼り付けて Enter。
   メッセージ ID（数字）だけでも動きますが、その場合は会話 ID を照合しません。
3. 探したい本文で覚えている言葉があれば入力して Enter（任意）。その言葉を含む文面を、残っているデータ全体から探します。
   複数あるときは 1 つずつ入力し、無ければ（または入れ終えたら）何も入れずに Enter。2 文字以上、8 個まで。
4. 解析元を矢印キー（↑↓）で選び、Enter で決めます。はじめから選ばれているのが通常の選択です。
   - 「この PC の標準の Teams 保存データを探し、保全コピーを取って解析する」（はじめから選択済み）。保存先が 2 つ以上見つかったときは一覧が出ます。はじめは全部が選択済みで、外したいものに ↑↓ で移動してスペースで外し、Enter で決めます。1 つだけならそのまま進みます。
   - 「採取済みのフォルダーを指定する」。`*.indexeddb.leveldb` そのもの、それを含むフォルダー、またはプロファイルやキャッシュのコピーのパスを入力します。続けて読み方を選びます（「保全コピーを取ってから解析する」がはじめから選択済み）。
5. 結果の保存先（既定は `ドキュメント\TeamsMessageHistory\<日時>`）を Enter で確定。
6. 解析、痕跡走査、スレッド全体の探索の順に進み、画面に判定の要約が出ます。本文は保存先の `result.txt` の先頭で読めます。

リンク・言葉・フォルダーのパスは文字で入力し、選択肢は矢印キーと Enter で選びます。数字キーを押すとその番号の選択肢へ移動します（Enter で決定）。
キー入力を受け取れない実行（入力や出力をファイルやパイプにつないだ場合）では、同じ質問が番号の入力になります。

コマンドラインでも使えます。

```
TeamsMessageHistory.bat -Link "<リンクまたはメッセージID>" [-Source <フォルダー>]... [-Out <保存先>] [-InPlace] [-Diag] [-TraceSource <フォルダー>]... [-NoTraces] [-Word "<言葉>"]... [-NoThread]
```

`-Source` を省略すると標準の保存先を探します。`-InPlace` は指定フォルダーを複製せず読み取り専用で解析します。`-TraceSource` は痕跡走査に加える採取済みフォルダー（通知データベースやキャッシュのコピー）、`-NoTraces` は痕跡走査を行いません。`-Word` は覚えている言葉（複数指定可）、`-NoThread` はスレッド全体の探索を行いません。`-Link` を付けた実行では何も尋ねず、今までどおり引数だけで進みます。

## 結果の読み方（result.txt）

先頭から順に、次の節があります。

1. `[判定（IndexedDB の保存データ）]` IndexedDB だけの判定です。「見つかった」「読めなかった」「見つからない」「解析元なし」を区別します（下記）。
2. `[痕跡（通知・キャッシュ）]` 痕跡走査の 1 行要約（対象 ID の一致数、別会話の同じ ID、会話 ID・親 ID だけの一致、走査した保存元の数と範囲）。
   続く `[スレッド全体の探索]` は、その探索の 1 行要約（件数）です。
3. `[本文候補]` IndexedDB に残っていた対象メッセージの本文。候補ごとに全文、出現回数、保存順序、`properties.edittime` の値、対応する `bodies\body-NN.txt` / `.html.txt` を示します。番号は全体の通し番号で、本文ファイルの番号と同じです。
4. `[痕跡の本文（未確認）]` 通知データベース・キャッシュの記録のうち、対象のメッセージ ID と `content` を同じレコードから読めたものを、本文が同じものごとに 1 つに束ねて全文で示します。各項目に、出所（キャッシュ / 通知 DB）、会話照合（一致・不明・未照合）、JSON の読取が完全か、出典ファイルの写しの切り詰め、レコードの `properties.edittime`、`IndexedDB の本文候補と同じ本文` か `IndexedDB の本文候補には無い本文` か、出典ファイル（`traces\hit-NNN-*.txt`）を付けます。これらは対象メッセージの版だと証明されたものではなく、本文候補には数えません。会話照合が「不明」のものは、同じ ID を持つ別会話の記録である可能性が残ります。
5. `[スレッド全体の探索（未確認）]` 下の「スレッド全体の探索」を参照。
6. `[解析元]`、`[詳細な根拠]` 解析元ごとのファイル統計、本文候補の出現ごとの出典（ファイル・保存順序・ストア・キー・レコード内の位置）、読めなかった候補。
7. `[痕跡（IndexedDB 以外）]` 痕跡の一致ごとの出典（保存元、ファイル、位置、会話照合、レコードの id・`content`、キャッシュ項目の位置と応答日時）と、件数の画面。

`result.txt` の末尾の `[所要時間]`（`result.json` では `timingsSeconds`）に、段階ごとの秒数が出ます: 起動時のコンパイル（BAT から起動した場合）、保全コピー（複製と SHA-256）、IndexedDB の解析、保全コピーの再ハッシュ、診断の集計、痕跡走査の全体とその内訳（ファイルの読取〔走査側が待った時間〕と先読みスレッドの読取時間の合計、生バイトの照合、ファイル内の gzip の探索、キャッシュ項目の構造読取、本文の展開〔符号化ごと〕、展開後の照合、出典ファイルの書出し）、スレッド全体の探索とその内訳、合計。通常の実行では画面の最後にも 1 行で出ます（`-Diag` の画面には出しません）。入力待ちの時間は含みません。

痕跡走査のファイルは、複数のスレッド（最大 8）で先に読み込み、照合は今までどおり 1 つずつ同じ順で行います。読む内容・上限・件数・出典の番号は変わりません。環境変数 `TMH_READ_THREADS` でスレッド数を変えられ、`1` にすると 0.1.6 までと同じく 1 ファイルずつ読みます（速さの比較用）。先読みのために、読み込み済みで未照合のファイルを最大 256MB ほどメモリーに持ちます。

次のものは本文として扱わず、件数と出典だけ残します: 隣のレコード（同じ応答に並ぶ別 ID の投稿）、会話 ID・親投稿 ID だけの一致、別の会話の同じ ID、ID が別レコードのフィールド内にあるもの、`content` を同じレコードから読めない近傍の断片。キャッシュに記録された応答日時は編集日時ではなく、編集日時として表示しません。

### スレッド全体の探索（未確認）

本文候補の照合は「`id`（または `messageMap` のキー／`clientMessageId`）が対象と等しい記録」だけを本文として受け付けます。スレッド全体の探索は、それ以外に残っているものを項目名に関係なく集めて、次の 5 つに分けて出します。どれも対象メッセージの版だと確認できたものではなく、本文候補には数えません。

- **入力した言葉を含む文面**: 言葉を含む文面をすべて。ID が近くに無い文面（下書きの残り、別の会話の記録、キャッシュの断片）も含みます。IndexedDB は復号した文字列（HTML のタグを外した文面。大文字小文字は区別せず、改行をまたぐ言葉も一致）、通知データベースとキャッシュは生のバイト・gzip の中・展開したキャッシュ本文から、言葉の前後の読める範囲を出します。
- **対象のメッセージ ID を別の項目に持つ記録の文面**: `id` 以外の項目（項目名は問わない。数値で持つ場合、リンクや HTML の中に含まれる場合、項目名そのものが ID の場合を含む）に対象の ID がある記録の、表示文らしい項目すべて。通知の一覧の抜粋、引用返信の引用部分、通知データベースのトーストの文面などがここに出ます。
- **本文候補の一部と同じ並びを含む文面（自動）**: 見つかった本文候補から 8 文字の並びを最大 6 個取り、それを含む別の文面を探します。編集前の版が編集後と言い回しを共有していれば、ID が無くてもここに出ます。本文候補そのものと、その抜粋は除きます。
- **同じスレッド（親投稿 ID）の記録の文面** と **同じ会話（会話 ID）だけが一致する記録の文面**: 対象の ID は持たないが、同じスレッドや同じ会話に属する記録の文面。

各文面には、`= 本文候補 N と同じ本文`／`本文候補 N の一部と同じ（抜粋）`／`本文候補には無い文面` の別、見つけ方ごとの出現数、出所（IndexedDB／通知・キャッシュ）、出典（保存元・ストア・キー・項目、または `traces\hit-NNN-*.txt`）、ID のあった項目名を付けます。同じ文面は 1 つに束ね、IndexedDB の記録は保存された版ごとに 1 件と数えます。`result.txt` には区分ごとに 30 種まで（1 つ 3000 文字まで）を載せ、全件は `thread\texts.txt` にあります。

読むときの注意:

- 「本文候補には無い文面」は、編集前の版とは限りません。別の投稿、引用に添えた返信、通知の題名などもここに入ります。対象メッセージの旧い本文かどうかは内容で判断してください。
- メッセージ ID は送信時刻の数値なので、時刻や版を表す項目（項目名に `time`／`version`／`utc` を含むもの）が同じ数値を持つことがあります。これは参照ではなく時刻の一致とみなし、件数だけを注記します。
- 人名の項目（項目名に `name` を含むもの）、ID・URL・時刻の形をした値は文面として扱いません。
- 言葉は 2 文字以上。通知・キャッシュ側の生バイトの照合は、UTF-8・UTF-16・JSON の `\uXXXX` 表記での完全一致です（4 バイト未満になる短い英数字、文字装飾のタグで分断された言葉、未対応の圧縮の中は見つけられません）。IndexedDB 側は、ID か言葉のバイト列を含む記録だけを復号して調べるため、文字装飾のタグで分断された言葉は、その記録が ID を含まない限り見つけられません。
- 文面の種類が上限（区分ごとに 1500〜2000 種）を超えた分、言葉の一致が 1 つの領域で 50 件を超えた分は「打切り」として件数に出し、その先は調べていません。

### 判定（IndexedDB）

- **見つかった**: 本文候補が 1 つ以上ある。候補が複数なら、同じメッセージ ID の異なる本文（編集前後など）が残っていたことを示します。
- **読めなかった**: メッセージ ID の文字列を含むデータはあるが、復号できない・未対応の形式・外部 blob ファイルが無い。該当箇所と理由を列挙します。外部 blob や圧縮に包まれていて中身を確認できない版は、キーが対象の会話やメッセージを指していれば候補として、そうでなければ別枠（`unreadableWrapped`）として数えます。
- **見つからない**: IndexedDB の保存データに該当する本文が無い。「読めなかった候補」、外部 blob／圧縮の読取失敗、`[痕跡の本文]` もあわせて確認してください。
- **解析元なし**: IndexedDB の保存データが見つからない。痕跡走査の結果だけが出ます。

同じメッセージ ID が別の会話 ID にあった場合は「別の会話」として除外し、混ぜません。チャネルの返信リンクでは
`messageId`（返信そのもの）を対象にし、`parentMessageId`（親投稿）は目印としてだけ表示します。

### 保存順序と編集日時は別物です

出力の「保存順序 seq=…」は LevelDB のシーケンス番号で、端末にその版が書き込まれた順です。編集した日時ではありません。
編集日時は、レコードに `properties.edittime` がある場合にだけ、その値を表示します。どの候補が最終版かは、最新の生存レコードと
`properties.edittime` を見て判断してください。

### 出典の種類（IndexedDB）

- `[レコード版]`: object store のレコードの版（上書き前の旧版を含む）。`live` でない版は削除マーカーです。
- `[undoログ: 上書き前の旧値]`: IndexedDB が上書き前に控えた旧値。本体の旧版が消えた後も残ることがあります。
- `[孤立blob: 参照の無い blob ファイル、保存順序不明]`: `*.indexeddb.blob` に残っているが、どの版の参照からも指されていないファイルを単体で読んだもの。本文は読めても、いつ保存された版かは分かりません。
- 位置 `...originalNonLieMessage` は、編集中にクライアントが保持する編集前の控えです。
- 「値は外部 blob ファイル」の版は、レコード本体が参照だけを持ち、本文は `*.indexeddb.blob` 配下のファイルにあります（大きな値）。版ごとに「その版の区間に書かれた blob 参照」を使って読むので、旧版の本文を最新版の本文で置き換えることはしません。旧版の blob ファイルが消えていれば、その版は「読めなかった」として出します。

## 読む場所

IndexedDB は次の標準の保存先だけを見ます（ディスク全体は探しません）。

- 新しい Teams: `%LOCALAPPDATA%\Packages\MSTeams_*\LocalCache\Microsoft\MSTeams\EBWebView\<プロファイル>\IndexedDB\https_teams.*.indexeddb.leveldb`（隣の `*.indexeddb.blob` も複製）
- 従来の Teams: `%APPDATA%\Microsoft\Teams\IndexedDB\https_teams.*.indexeddb.leveldb`
- Edge / Chrome のプロファイル内の `IndexedDB\https_teams.*.indexeddb.leveldb`

痕跡走査の範囲は実行の仕方で決まります。

- 標準の保存先を使った実行: この PC の通知データベース（`%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db` と `-wal` / `-shm`）と、解析した保存データと同じプロファイルのキャッシュ（`Cache\Cache_Data`、`Service Worker\CacheStorage`）。IndexedDB が無い PC では、通知データベースと標準の場所にある Teams プロファイルのキャッシュ。
- 採取済みフォルダーを指定した実行: 指定したフォルダーの範囲だけ（同じプロファイル配下のキャッシュ、配下にあるキャッシュや通知データベースのコピー）と `-TraceSource` のフォルダー。この PC の稼働中プロファイルと通知データベースは走査しません。

キャッシュは、生バイトの走査に加えて項目の構造でも読みます。Chromium の blockfile 形式（`index` + `data_0`〜`data_3` + `f_xxxxxx`）と simple 形式（`<hash>_0`）の両方に対応し、項目ごとにキー（URL）・応答ヘッダー・本文を分け、ヘッダーの Content-Encoding に従って本文を展開（gzip / deflate / br。br は Google 公開の Brotli 復号器を `src\brotli` に収録）してから ID を照合します。zstd などは「未対応」、展開できないものは「失敗」として件数に残ります。blockfile では索引から辿れなくなった項目（削除・退避済みで、ブロックが再利用されていないもの）も、記録されたキーのハッシュが一致する場合に限って読み、常に「索引外」と表示します。

## 限界と注意

- 残っているものしか出せません。LevelDB の整理（compaction）などで旧版が消える場合があります。「見つからない」という結果だけでは、旧版の消失や編集の有無は断定できません。
- 通知は要約のことがあり、キャッシュに会話の応答が残るかは設定と通信の条件次第です。痕跡の 0 件は「この走査では見つからず」で、過去の有無を示しません。
- 痕跡の本文は、対象メッセージの版だと証明されたものではありません。会話照合が「一致」でも、記録そのものが同じメッセージのものかは利用者が内容で判断してください。
- 保存データは Teams が動いたまま複製・走査するため、同一時点の整合性は保証しません。複製できなかったファイルは `manifest` に、走査できなかったファイルは `traces.txt` と `traces\traces.json` に残ります。
- Teams の内部構造（データベース名、`replychains` / `messageMap`、フィールド名、API 応答の形）は非公開で、将来変わることがあります。本ツールは構造を決め打ちせず、メッセージ ID を含むレコードをすべて復号して照合します。
- 大きな保存データ（数百 MB）では複製と解析に時間がかかります。

## 補助の入口

- **診断（1 画面の要約を写真で共有する）** `TeamsMessageHistory-Diag.bat`（または `-Diag`）は、通常どおり解析した後に画面を消して、本文・氏名・ID・組織名・フォルダー名・パス・URL・入力した言葉を含まない要約を表示し、`diag.txt` にも書きます。最終画面は 96 桁 × 25 行以内です。本文候補や痕跡の詳細は `result.txt` / `result.json` に残ります。
  末尾の 3 行 `[スレッド探索/未確認]` が、スレッド全体の探索で何が何件見つかったかです: 別項目に対象 ID を持つ記録の数とその文面の種類（うち本文候補に無いもの）、打切り、言葉の個数・一致数・文面の種類、本文候補と同じ並びを含む別の文面の種類、親投稿 ID の記録、会話 ID だけの記録。対話式で言葉も入れるときは、この BAT で同じ流れになります。
- **追加診断（既存の結果フォルダーから、再取得なし）** `TeamsMessageHistory-Review.bat`（または `-Review [<結果フォルダー>]`）は、保存済みの `result.json` だけを読み、複製できなかったファイルの種別と原因、読めなかった包まれた値の内訳を固定ラベルと件数だけの 1 画面に出します。出力は結果フォルダーの隣の `<結果フォルダー名>-review` です。
- **痕跡だけの走査** `TeamsMessageHistory-Traces.bat`（または `-Traces [-Link <リンク>] [-TraceSource <フォルダー>]...`）は、通知データベースと WebView2 キャッシュだけを走査し、件数だけの 1 画面（`traces.txt`）と `traces\` を出します。本体の実行に含まれる痕跡走査と同じ処理です。

## 出力ファイル

| ファイル | 内容 |
| --- | --- |
| `result.txt` | 判定、本文候補（全文）、痕跡の本文（未確認）、出典、読めなかった候補、痕跡の一致ごとの出典 |
| `result.json` | 同じ内容の機械可読版（LevelDB の警告、データベース一覧、統計、痕跡の候補と版を含む） |
| `bodies\body-NN.txt` / `.html.txt` | 本文候補ごとのテキストと、生の HTML（HTML 表現が複数ある場合は `-vN` 付き）。生 HTML はブラウザーで開かれないよう `.html.txt` という拡張子で保存します |
| `preserved\` | IndexedDB の保全コピーと `manifest-NN.json`（元ファイルのサイズ・更新時刻・SHA-256・複製の成否） |
| `traces.txt` | 痕跡走査の件数だけの画面 |
| `traces\` | 痕跡の出典: `traces.json`（保存元・キャッシュ項目・一致の一覧）と、一致ごとの `hit-NNN-*.txt`（周辺の窓、同種の要素、一致を含む JSON レコード）。本文の断片を含むため共有しないでください |
| `thread\` | スレッド全体の探索で集めた文面: `texts.txt`（全件、全文）と `thread.json`（機械可読。ID のあった場所の集計を含む）。本文を含むため共有しないでください |
| `diag.txt` | 診断要約（`-Diag` の画面と同じ内容。末尾にスレッド全体の探索の件数） |

## 動作確認の要点（2026-10-10 時点）

- 0.1.7 で加えたスレッド全体の探索と矢印キーの選択は、開発機（macOS）で、合成データと自宅 PC の実データ 1 件に対して動作を確かめた段階です。Windows の実機（Windows PowerShell 5.1 でのコンパイル、コンソールでの矢印キーと日本語の入力）での確認はこれからです。仕事用テナントのチャネル返信で編集前の本文が出るかは未確認で、出ることを約束するものではありません。
- 0.1.6 は Windows 11・Windows PowerShell 5.1・非管理者の実機で確認しました。通常の BAT に引数を渡す経路では、個人用 Teams の自分宛てチャット 1 通の編集前後の 2 本文を全文で取得しました。採取済みフォルダーの指定では稼働中の通知データベース・キャッシュを混ぜず、標準の実行では通知データベースとキャッシュも走査しました。
- IndexedDB が無い合成プロファイルでは、通常の BAT の対話式・引数の両方から結果が出ました。400 字を超える本文の末尾、同じ本文の束ねと出典、別 ID・別会話の除外、会話フィールドの無い記録の「不明」を確認しました。補助の 3 入口も動作し、診断は 96 桁 × 25 行に収まりました。試験に使った元ファイルの SHA-256 は不変でした。
- 実データで旧本文を回収できたのは、個人用の自分宛てチャット 1 通（編集前後の 2 本文）だけです。仕事用テナントやチャネル返信での編集前本文の回収、削除されたメッセージ、通知やキャッシュに旧本文が残る条件は未確認です。zstd と共有辞書系の符号化は未対応です。
